PHP flaw sets off global patching scramble

In one sentence
Two critical PHP flaws patched on 21 October are being actively exploited, and operators on old branches or shared hosting may struggle to fix them quickly.

A pair of flaws in PHP, the scripting language behind a large share of the web, were fixed in an emergency release on 21 October. They are now being used in real attacks. Anyone running an unpatched copy of PHP that serves web pages is potentially exposed. Many of the people responsible for those copies do not control when, or whether, they can update.

The two bugs, tracked as CVE-2026-109618 and CVE-2026-109619 and nicknamed "php2shell", are rated 9.2 out of 10 on the CVSS 4.0 scale. The PHP project says an unauthenticated attacker can exploit both remotely. The US cyber agency CISA put both on its Known Exploited Vulnerabilities list on 26 October and gave federal civilian agencies until 29 October to fix them.

What is broken

The flaws are memory-handling errors. In the first, if a server runs out of memory while request data is only partly set up, the cleanup code treats that half-built data as valid. In the second, a use-after-free, leftover state from one request points to memory that has already been released. A later request handled by the same worker process can then use it. PHP also confirms that memory disclosure is possible.

PHP says any installation serving web requests is at risk. That covers PHP-FPM, Apache's mod_php, php-cgi, FrankenPHP and LiteSpeed. The project rates mod_php highest, because a demonstrated exploit can fire before any application code runs. The practical point is that a site does not need a badly written plugin to be vulnerable. The weakness is in the language runtime itself.

Security firm Calif traced the earliest affected code path back to PHP 5.4.0, according to Tenable's analysis. The code is old.

Who has been hit, and how many are exposed

The fixes are in PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35. Those are the only branches that get official patches.

Exploitation began before the fix did. Amazon's threat-intelligence team saw an attempt against its honeypot servers on 17 October, four days before disclosure, and more on the day of release. Cloudflare reports early attacks and has pushed firewall rules to block known exploit paths. Trail of Bits said on 26 October that working exploits run against unpatched PHP 8.2 through 8.5. PHP's own team said it found no functional exploit at release, and public exploit code now circulating is unverified. One researcher, Adel Karimi, reported breaking into three honeypots running PHP 8.4.26, though the setup was deliberately favourable and says little about reliability elsewhere.

Estimates of the exposed population vary widely, which suggests nobody has an exact count. Palo Alto's Cortex Xpanse put potentially vulnerable instances at over 22.6 million. An independent estimate cited by Tenable is over 1.3 million internet-exposed hosts. A Shodan search finds over 1.9 million internet-facing hosts running PHP, though that counts PHP, not vulnerability. For scale, W3Techs says PHP is used by 69.3% of sites whose server-side language is known.

Who can patch quickly

The answer splits by how much control an operator has.

A company running its own servers on a current PHP branch can update within hours. Even then, installing the new package is not enough. Processes already running keep the old code in memory, so PHP workers must be restarted. Google Cloud advises capturing worker memory from any server showing signs of probing before restarting, since a restart erases the evidence.

Operators on older branches are in a worse position. PHP 7.4 through 8.1 get no official release, only minimal source backports for people who build PHP themselves. PHP 5.4 through 7.3 get nothing from the project, and users must rely on their Linux distribution or a paid long-term-support vendor. CISA's advice for anyone who cannot update promptly, or who runs 8.1 or earlier, is blunt: take the system offline.

The third group is the least visible. CISA stresses that PHP is often embedded in other software, so its presence may not be obvious, and tells organisations to inventory every system running any PHP version. Shared-hosting customers and owners of forgotten content-management installs depend on someone else to patch, or on nobody noticing the site at all. Neither is a plan.

The release itself is also imperfect. PHP 8.4.27 and 8.5.12 can crash processes in some applications using the SimpleXML extension. The cause is a separate garbage-collector change, not the security fix, and a correction was merged but had not shipped as of 26 October. Some operators will have to choose between a known crash risk and a known exploit.

For those who cannot patch at once, there are partial measures. Setting memory_limit to -1 in a way applications cannot override reduces exposure to the first flaw, and disabling session.upload_progress reduces exposure to the second. Both are stopgaps, and PHP says updating is the only complete fix. Cloudflare's rules help only for traffic routed through its network.

What to watch

The next markers are the 29 October federal deadline and the fix for the SimpleXML regression, which will show how fast the patched population grows. A separate bug, CVE-2026-115560, disclosed on 23 October, concerns session upload progress; PHP advises disabling that setting until its next bugfix release. Also watch for the first verified public exploit, and for scan data showing how many PHP hosts are still unpatched a week after disclosure.
