HSBC code exposure linked to crypto theft: unconfirmed

In one sentence
An aggregator links HSBC to a crypto theft, but trade reports point to a vendor-code incident across 178 sites, about $7,000 traced so far, and no HSBC statement.

A report from an investor-research aggregator ties HSBC to a crypto theft through exposed code. The question that decides how much it matters is whether the bank itself was breached or a third party was. The available evidence points to a third party. It also leaves HSBC's own account unheard.

The item that reached the desk cites one source, Simply Wall St, which gives no amount, date or description of the code. Independent trade reporting fills part of that gap. It suggests the story is a supply-chain incident rather than a break-in at the bank.

What the secondary reports say

According to crypto and security outlets, an attacker exploited a flaw in the account signup flow of Optimizely, a web-experimentation vendor, on 16 November. That let them plant malicious code that reached 178 organisations' websites. HSBC was among them, alongside the BBC and the hardware-wallet maker Ledger.

The reported behaviour of the code was specific. It scanned pages for wallet addresses across Bitcoin, Ethereum, Solana, Tron and five other networks, and swapped in the attacker's own. It also reportedly copied clipboard text and skimmed card numbers, cookies and screenshots. One report adds that it served exploit kits aimed at older iPhones.

One blog says the code reached HSBC through eleven regional sites. The route matters. A web-testing vendor's script is loaded from the vendor on every page view, so an attacker who controls the vendor's pipeline can reach a bank's visitors without touching the bank's servers.

How much was taken

The sum is small. Wallets linked to the attack had received about $7,040, mostly in Bitcoin, by Monday evening, according to the security firm Report URI. Bloomberg could not independently verify that figure, and it covers only what had arrived at known addresses. Card-data skimming would not show up in it.

Optimizely has said it "blocked the vulnerable path, removed the injected code and contacted customers directly." The reporting reviewed includes no HSBC statement, no regulator notice and no incident report.

What is established and what is not

The evidence supports a narrow claim: HSBC web pages were among many that received injected third-party code. The aggregator's framing, a link between the bank's code exposure and a crypto theft, goes further than that. Nothing seen shows HSBC customers losing funds, HSBC systems being breached, or the bank's own code being the source. The "exposure" appears to be the vendor's code running on HSBC pages. The aggregator's description of investors "weighing" the implications is not evidence of any confirmed impact either.

The $7,040 total is also small beside the largest crypto thefts. For a bank of HSBC's size, any direct financial effect from this episode looks minor on the numbers available. The more lasting issue is third-party script risk. Regulators already ask banks to account for it in their outsourcing and operational-resilience rules.

What to watch

Three things would change the assessment. One is an HSBC statement saying whether any customer data or funds were affected on the 11 sites reportedly touched. Another is a notice from a regulator such as the Financial Conduct Authority or Prudential Regulation Authority. The third is Optimizely's fuller post-incident account of which customers' pages received the code and for how long. Until one of those appears, this is a watch item, not a bank breach.
